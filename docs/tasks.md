# Kineq Tasks

## Current focus

The clinical flow MVP (Paciente → Turno → Iniciar atención → Pantalla de atención → Ficha inicial → Cargar evolución → Finalizar turno) is implemented end to end, including a tabbed-workspace redesign of the attention and patient-detail screens. Ficha Inicial was rebuilt (see "Ficha Inicial — rediseño estructurado" below) from a flat text-only form into a catalog-backed clinical workspace, then refined with a round of incremental adjustments (see "Ficha Inicial — ajustes incrementales" below): per-consultorio custom catalog items, automatic/backend-authoritative section state, an "Alertas clínicas" summary card, and a general Estudios tab replacing the old Archivos placeholder. Most recently: clinical authorship, the Usuario↔Profesional link, and turno-table navigation/permissions were reworked (see "Autoría clínica, vínculo Usuario–Profesional y permisos" below) — this is a real behavior change, not just additive: writing clinical content now requires a linked Profesional even for Administrador. Current focus is closing the remaining verification gaps — see "Known gaps / next priorities" below — before moving to new functional scope.

Login screen, Configuración tables, and the Evoluciones table also got focused UI passes this session (icon-based row actions, responsive tabs, compact non-scrolling table, soft-delete) — see their own bullets below.

### Ficha Inicial — rediseño estructurado (catálogo clínico)
Replaced the flat, mostly-free-text `FichaInicial` (22 fields, 2 semi-structured via a single `estado`+`detalle` pair each for alergias/medicación) with a catalog-backed clinical workspace, closing the gap against the legacy reference system's antecedentes/alergias/quirúrgicos checklists without copying its UI or creating one column per condition.

**Data model** (migration `20260805182006_add_ficha_inicial_catalogo_clinico`, mostly additive):
- New `CatalogoClinicoItem` (global/system catalog, categorías `ANTECEDENTE_PERSONAL` / `ANTECEDENTE_FAMILIAR` / `PROCEDIMIENTO_QUIRURGICO` / `ALERGIA`, seeded in `backend/src/seedCatalogoClinico.ts` — ~70 items, shared by `seed.ts` and `seedIafsDemo.ts`).
- New `FichaAntecedente` (personal/familiar/quirúrgico, one table discriminated by `catalogoItem.categoria`, `SI`/`NO` only — `NO_INFORMA` is implicit-by-absence, never a persisted row), `FichaAlergia` (catalog item or `nombreLibre`, reacción/gravedad/observaciones), `FichaMedicacion` (no catalog, free-text `nombre`), `FichaEstudioComplementario`, `FichaSeccionEstado` (per-section `PENDIENTE`/`EN_PROGRESO`/`REVISADA`).
- `FichaInicial` gained hábitos (tabaquismo/alcohol/sedentarismo/ejercicio) and contexto gineco-obstétrico (menarca/menopausia/gestas/partos/abortos) as direct scalar columns — no separate 1:1 tables, no benefit over the existing flat-row convention. Dropped `alergiasDetalle`/`medicacionDetalle` (superseded by the structured lists; confirmed zero real data loss, only empty-string rows existed in dev). `antecedentesPersonales`/`antecedentesFamiliares`/`cirugias` free-text fields were **kept** as supplementary notes alongside the new structured lists, not replaced.
- Per-consultorio custom catalog items were deferred out of v1 for a real technical reason (MySQL doesn't dedupe `NULL` in a unique index) — **this was resolved in the "ajustes incrementales" round below**, see that section for the actual model.

**Backend**: endpoints under `/api/pacientes/:id/ficha-inicial/{antecedentes,alergias,medicacion,estudios}` plus `PATCH`/`DELETE` on `/api/ficha-{antecedentes,alergias,medicacion,estudios}/:id` and `GET /api/catalogo-clinico`. Same `requireRole(...CLINICAL_ROLES)` + consultorio-scoped 404 pattern as the existing ficha-inicial routes. (The original `PATCH .../secciones/:seccion` route for manually setting section state was removed in the ajustes-incrementales round — see below.)

**Frontend**: `InitialAssessmentPanel` is now a workspace (`AssessmentSectionNav` rail — Resumen/Motivo/Antecedentes/Seguridad/Contexto y Hábitos/Dolor y función — instead of the previous 4 flat subtabs) backed by the new `useFichaInicial` hook. New components: `ClinicalAntecedentesSection` (search-to-add + list + "Ver todos" drawer, shared across the 3 antecedente categorías), `FichaAllergyList`, `FichaMedicationList`, `FichaEstudiosList`, `InitialAssessmentSummary`. `ClinicalSummaryPanel`'s alert badges now derive from the structured `alergias`/`antecedentes` arrays instead of the old single free-text `alergiasDetalle` field.

**Not implemented** (matches the explicit out-of-scope list agreed before implementation): coded diagnoses, professional/digital signature, advanced clinical audit trail, real document uploads, patient portal, AI, React component tests (see "Known gaps" below — pre-existing gap, not newly introduced).

### Ficha Inicial — ajustes incrementales

A follow-up round of adjustments on top of the rediseño above, explicitly scoped as additive/incremental (not a redesign): per-consultorio custom catalog, backend-authoritative automatic section state, an "Alertas clínicas" summary card, a general Estudios tab, and a fix for the Resumen clínico antecedentes display. Migration `20260805205254_ficha_inicial_catalogo_por_consultorio_y_alertas`, fully additive.

**Catálogo por consultorio** — `CatalogoClinicoItem` gained `esSistema Boolean` and nullable `consultorioId`, with `@@unique([consultorioId, categoria, codigo])` (this only truly enforces uniqueness for non-null `consultorioId` rows — global/system items still rely on controlled seeding, per the original MySQL-NULL-dedup constraint). `POST /api/catalogo-clinico` (creates a custom item scoped to the caller's consultorio, `CLINICAL_ROLES` only, 409 on duplicate name within the same categoría+consultorio) and `DELETE /api/catalogo-clinico/:id` (soft-deactivate, system items and other consultorios' items 404) are new. `GET /api/catalogo-clinico` now returns system items (`consultorioId: null`) **plus** the caller's own consultorio's custom items only — never another consultorio's. Frontend: the antecedentes/alergias search boxes now offer "+ Agregar '<query>'" when nothing matches, which creates the catalog item and attaches it in one step (search-first, create-only-if-not-found, per spec).

**Automatic section/ficha state** — the old `PATCH /api/pacientes/:id/ficha-inicial/secciones/:seccion` route (manual state override) was deleted, and the manual "Estado de revisión" `<select>` was removed from the UI entirely (`SeccionRevisionControl` component deleted). `recomputeSeccionesEstado()` in `app.ts` is the single function computing MOTIVO/ANTECEDENTES/SEGURIDAD/HABITOS/DOLOR_FUNCION state (PENDIENTE/EN_PROGRESO/REVISADA) and the ficha's own `estado` (BORRADOR/COMPLETA), called after every mutation that could affect either — never duplicated per-endpoint. The client-sent `estado` field is ignored on `PATCH .../ficha-inicial` (whitelist no longer includes it).

**Alertas clínicas** — `FichaAntecedente`/`FichaMedicacion` gained `esAlertaClinica Boolean` (explicit opt-in flag, checkbox in their edit forms; alergias count as alerts by default with no flag needed). No new backend endpoint: the flag rides along on the existing `ficha.antecedentes`/`ficha.medicaciones` arrays, and `frontend/src/utils/clinicalAlerts.ts` (`computeAlertasClinicas`) is the single shared function deriving alert state — used by both the new "Alertas clínicas" summary card (`PatientSummaryCards`, replaced the old "Evoluciones" card) and its detail modal (`ClinicalAlertsDetail`). Three states, never conflated: **sin-alertas** (Antecedentes + Seguridad clínica sections both REVISADA, nothing flagged), **activa** (at least one alergia/flagged antecedente/flagged medicación), **pendiente** (those sections not fully reviewed yet — "Información pendiente", not a false "no alerts"). Recepción never sees real alert data because `useFichaInicial` never fetches the ficha for non-`CLINICAL_ROLES` users in the first place (same existing gate, not a new check).

**Estudios tab** — moved out of the Ficha Inicial workspace entirely (no more "Estudios" entry in `AssessmentSectionNav`) into its own top-level tab (`FichaEstudiosTab.tsx`), replacing the old Archivos/`DocumentsPlaceholder` placeholder tab (that component is now deleted, it had no other callers). Each estudio row has a "Subir archivo" icon button with a `title="Carga de archivos próximamente"` tooltip and a no-op `onClick` — no `alert()`, no upload infra; the row already carries `fileId`/`attachmentId` readiness in mind for when real uploads are built. Empty state and copy match the agreed wording.

**Resumen clínico antecedentes fix** — the old code concatenated every positive antecedente into one long comma-joined badge string. `AntecedentesSummaryGroups.tsx` + `groupAntecedentesPositivos()` (also in `clinicalAlerts.ts`) now group by categoría (Personales/Familiares/Quirúrgicos), show up to 3 chips per group with alert-flagged items sorted first, and a "+N más" button opening a modal with the full list — reused as-is by `ClinicalSummaryPanel` (the fix target) and available for any future compact antecedentes display. Distinguishes "Sin antecedentes registrados" (Antecedentes section reviewed, genuinely empty) from "Antecedentes no relevados" (not reviewed yet).

**Renames** (UI labels only, enum/type keys unchanged — e.g. `HABITOS` stays `HABITOS`): "Revisar catálogo completo" → "Ver todos"; "Agregar '...' como alergia libre" → "Agregar alergia" (and the underlying flow now creates a catalog item instead of a free-text `nombreLibre` row); "Hábitos" → "Contexto y Hábitos" everywhere it's user-visible.

**Backend tests**: `app.test.ts` now has 70 tests (was 61) — added coverage for cross-consultorio catalog isolation, duplicate-name rejection, system-item immutability, inactive-custom-item historical preservation, automatic section/ficha state (including that client-sent state is ignored and the old manual route now 404s), and `esAlertaClinica` on create. **Frontend tests**: 31 across 3 files (`utils/turnoStatus.test.ts`, `utils/fichaInicial.test.ts`, new `utils/clinicalAlerts.test.ts` — grouping/ordering/filtering and all three alert states).

### Autoría clínica, vínculo Usuario–Profesional y permisos

A consolidation round covering who can write what. **This is a real behavior change, not additive**: previously an `ADMINISTRADOR` without a linked `Profesional` could write clinical content freely; now they can't, matching the explicit product requirement that nobody becomes an implicit clinical author. Diagnostic finding worth recording: most of the Usuario↔Profesional link machinery (schema 1:1 via `Usuario.profesionalId Int? @unique`, same-consultorio validation, 409-on-duplicate, the "Profesional vinculado" field in `UsuarioFormModal.tsx`) **already existed** before this round — the actual gaps were the reverse link (from `ProfesionalFormModal.tsx`), the blanket authorship gate, and a few role restrictions.

**Autoría automática** — `requireProfesionalVinculado()` (`backend/src/auth.ts`) now returns **403** (was 400) and is called unconditionally — Administrador included, not just when `rol === PROFESIONAL` — at the top of every clinical write: `POST/PATCH/DELETE /api/evoluciones`, `PATCH /api/pacientes/:id/ficha-inicial`, and `POST/PATCH/DELETE` for antecedentes/alergias/medicación/estudios. The client can no longer send an arbitrary `profesionalId` — it's silently ignored and replaced by the caller's own vínculo. `FichaInicial.profesionalResponsableId` gets set on every one of those writes (folded into `recomputeSeccionesEstado()`'s optional `autorProfesionalId` param), not just the main ficha PATCH. `FichaEstudioComplementario` gained its own `profesionalId Int?` column (migration `20260805224016_estudio_profesional_id`, nullable FK `ON DELETE SET NULL`, additive) so each estudio records who created it.

**A previously-existing restriction had to be relaxed to make this possible**: `POST/PATCH /api/usuarios` used to reject `profesionalId` unless `rol === PROFESIONAL`. Since Administrador now *needs* a vínculo to write clinical content, that restriction is gone — any role can be linked to a Profesional. `UsuarioFormModal.tsx`'s "Profesional vinculado" select is now always visible (was `PROFESIONAL`-only), with a warning line when rol is `PROFESIONAL` and nothing's selected.

**Vínculo desde Profesionales (the actual gap)** — `PATCH /api/profesionales/:id` now accepts an optional `usuarioId` (number to link, `null` to unlink). Reassigning (linking a profesional that already has a different usuario) unlinks the old holder and links the new one inside a `$transaction`; trying to link a usuario that's already attached to a *different* profesional returns 409. `ProfesionalFormModal.tsx` (edit mode only — linking makes no sense before the profesional has an id) now has a "Usuario vinculado" select; `ConfiguracionProfesionales.tsx` fetches the usuarios list and filters to unlinked-or-linked-to-this-profesional, same pattern `ConfiguracionUsuarios.tsx` already used the other way around. One source of truth throughout: `Usuario.profesionalId`, never a duplicated field on `Profesional`.

**Permisos ampliados** — `ADMIN_DATA_ROLES` (`backend/src/auth.ts`, all four roles) now gates `POST/PATCH /api/pacientes` and `POST/PATCH /api/turnos/:id` (previously `ADMINISTRADOR`+`RECEPCION`, missing `PROFESIONAL`/`SUPERVISOR`). Paciente `observaciones` is no longer Administrador-only — all four roles get the same administrative field set. The existing "profesional solo sus propios turnos" ownership check inside `PATCH /api/turnos/:id` is untouched. Content clínico (evoluciones/ficha/estudios) stays `CLINICAL_ROLES`-only (`ADMINISTRADOR`+`PROFESIONAL`), now additionally gated by the vínculo.

**Modo solo lectura sin vínculo** — `useFichaInicial()` takes a new `canWriteClinical` param (defaults to the existing `canEditClinical` for backward compat); when false, autosave doesn't fire. `InitialAssessmentPanel.tsx` and `FichaEstudiosTab.tsx` wrap their fields in a disabled `<fieldset>` (cascades to every native input/select/textarea/button inside — including the antecedentes/alergias/medicación sub-components — without threading a `readOnly` prop through each one individually) plus a banner: "Tu usuario no está vinculado a un profesional...". The evolución forms in both `PatientDetailPage.tsx` and `AttentionPage.tsx` dropped the professional-picker `<select>` that a previous round of this same task had added (that picker let Administrador choose an arbitrary profesional — exactly what this round removes) in favor of automatic resolution + the same explanatory message when unlinked.

**Navegación de turnos** — `TurnosPage`'s row click (`onOpenTurno`) used to route into the patient/attention screen only for `Atendiendo` turnos; any other status opened the edit modal directly (that was `openTurnoDetails`, reused today as the *new* explicit action). Now every row click navigates to the patient/attention screen regardless of estado (states other than `Atendiendo` just show the same screen without a live timer, since `AttentionPage` was already conditioning its timer/finalizar-atención UI on `turno.status === 'Atendiendo'`, never assumed it). A separate pencil icon per row (`config-icon-button`, `stopPropagation()` on both click and keydown) opens the edit modal without navigating. No new turno-state transition was added — clicking a row never starts/changes atención.

**Foto de perfil placeholder** — a small pencil button over the sidebar avatar (`.avatar-wrapper`/`.avatar-edit-button`) opens a popover ("La carga de imágenes estará disponible próximamente."), closes on outside-click/Escape, no `alert()`, no upload wired.

**Backend tests**: `app.test.ts` now has 92 tests (was 74) — added coverage for: vínculo desde Profesionales (link/reassign/conflict/unlink/cross-consultorio/non-admin-403), autoría automática (client `profesionalId` ignored, 403 without vínculo, read-still-works-without-vínculo, `profesionalResponsableId`/estudio `profesionalId` set correctly), desvincular preserves history but blocks new writes, and the four-role pacientes/turnos permission widening. Two pre-existing tests were rewritten because they asserted the *old*, now-intentionally-reversed behavior (Supervisor 403 on turnos, rejecting a non-Profesional link) — not regressions, the same pattern as previous rounds in this doc.

**Not implemented** (explicitly out of scope, matches the task's own list): real photo/file upload and storage, advanced audit, clinical signature, configurable granular permissions, custom roles, email invitations, multi-site, patient portal, general redesign.

### Estadísticas (V1), extended clinical alerts, and evolution grouping

Three additive pieces of work, one Prisma migration (`20260814204620_add_ficha_alerta_campo_y_grupo_evolucion`, purely additive — new `FichaAlertaCampo`/`GrupoEvolucion` tables, `Evolucion.grupoId` nullable FK — no backfill, no data loss). Full detail lives in `docs/modules/statistics.md` (new) and the "Alertas clínicas: extensión a otros campos" / "Grupos de evolución" sections of `docs/modules/clinical-history.md` — this entry is the changelog summary.

**Estadísticas**: new page (`frontend/src/components/EstadisticasPage.tsx` + `EstadisticasCharts.tsx`), backed by a single isolated backend module (`backend/src/estadisticasRoutes.ts` + `estadisticasService.ts`, mounted in `app.ts` with one line, no reordering of the existing 1600+-line file). `GET /api/estadisticas/resumen` reuses `requireRole`/`requireAuth`/the same `PROFESIONAL`-self-scoping pattern already used by `POST /api/turnos`. Reports: 4 primary + 4 secondary KPI cards, evolution-of-turnos line chart (auto granularity: day ≤31d, week ≤120d, month beyond), estado donut (same colors as the Turnos agenda), sesiones-por-profesional bar chart + resumen table (both hidden for `PROFESIONAL`), actividad-por-especialidad donut (`Especialidad.color`, no new palette). Added **recharts** as the only new dependency (none existed; a hand-rolled SVG solution was rejected as more code to maintain than one small standard library for 4 chart types with tooltips/responsiveness). No new migrations or indexes for this part — reads existing tables only, existing `Turno` indexes already cover the filter patterns.

**Alertas clínicas manuales, extended to more fields**: previously `esAlertaClinica` only existed as a boolean column on `FichaAntecedente`/`FichaMedicacion` (row-based catalog entries). The free-text scalar fields on `FichaInicial` (Motivo, Diagnóstico de derivación, Traumatismos, Tratamientos previos, Enfermedades actuales, Dolor y síntomas, Limitaciones funcionales, Hallazgos iniciales, Observaciones clínicas, Estudios complementarios) had no equivalent. New table `FichaAlertaCampo` (row existence = the alert, no `activa` column) + `PUT`/`DELETE /api/pacientes/:pacienteId/ficha-inicial/alertas-campo/:campo`, gated by the same `requireProfesionalVinculado` as every other clinical write. **Deliberately not touched**: the existing `esAlertaClinica` columns and their endpoints — no migration of existing alert data into the new table, no unified alert model, no severity/expiry/acknowledgement/AI. `ClinicalAlertsDetail.tsx` gained a fourth group ("Otras alertas") alongside Alergias/Antecedentes/Medicación.

**Grupos de evolución**: new `GrupoEvolucion` entity (`nombre` + `color`, reusing the same curated palette as `Especialidad.color`) and `Evolucion.grupoId` (nullable). Purely visual/organizational — explicitly not a `Tratamiento`: no diagnóstico, plan de sesiones, objetivos, or estado de tratamiento. "Eliminar" a group (`DELETE /api/grupos-evolucion/:id`) only sets `archivedAt` — never deletes evoluciones, and archived groups can't be assigned to new evoluciones but keep showing on the ones that already had them. UI: "+ Nuevo grupo" button + modal (`GrupoEvolucionModal.tsx`, same `.modal-overlay`/`useModalDismiss` pattern as every other Kineq modal), a grupo selector on create/edit, a colored chip in `EvolutionTable.tsx`, and a "Ver por fecha | Ver por grupo" toggle (`frontend/src/utils/groupEvolucionesByGrupo.ts`, pure/tested function, grouping happens client-side over the already-loaded evolución list — no new endpoint needed for that).

**Also fixed in the same pass** (small, unrelated to the above but requested together): "Creá tu consultorio" register inputs weren't actually smaller than Login's (`.login-input` CSS was identical) — the real cause was `.login-card`'s fixed 440px width combined with the register form's 2-column rows (`.login-form-row`), which squeezed paired fields to ~170px; fixed with a `.login-card--wide` modifier (520px) scoped to `RegisterPage.tsx` only. Avatar edit-pencil badge switched from a hardcoded `bottom:-4px;right:-4px` offset to `bottom:0;right:0;transform:translate(35%,35%)` (proportional to the badge's own size, not a magic value tied to one avatar size). ### Bug-fix round: alertas/autosave races, click-to-navigate, grupos completion, rich text

Follow-up round on the previous one, fixing real bugs found via an actual click-through of the shipped UI (the previous round's own manual verification never exercised a live text-field autosave — it used a fragile selector that missed the real input — which is exactly why these went undetected until now) plus finishing two features that were left partially usable.

**Two independent, real bugs behind "Failed to save ficha inicial" / apparent content loss** (both found by reproducing the user's exact repro steps against a live browser, not by reasoning alone — see `docs/modules/clinical-history.md` "Bugs corregidos: pérdida de contenido y guardado roto" for the full diagnosis):
1. `useFichaInicial.ts`'s `refresh()` (called after any ficha-inicial mutation, including marking a manual alert) unconditionally overwrote `form` with the server's response — if a text-field autosave was still debouncing when the user triggered a `refresh()`-causing action, the just-typed text got silently discarded. Fixed with a `pendingRef` guard: `refresh()` now skips the `form` overwrite whenever there's an unsaved edit in flight.
2. Separate bug, not a race at all: `buildFichaPayload(form)` always sends the *entire* form on every autosave, including enum-typed fields (`alergiasEstado`, `medicacionEstado`, `tabaquismoEstado`, `alcoholEstado`, `sedentarismoEstado`, `menarcaEstado`, `menopausiaEstado`) defaulted to `''` until touched — and Prisma rejects `''` for a nullable enum column outright (500). This fired on the *first* autosave of *any* field in a brand-new ficha, no concurrency needed. Fixed in both layers: frontend sends `null` instead of `''` for those fields (root cause), backend also normalizes `'' → null` for the same fields at the API boundary (defense in depth, per "only validate at trust boundaries").

Also hardened `upsertFichaInicial` (shared by the main `PATCH` and by `getOrCreateFichaInicial`, which runs on every antecedente/alergia/medicación/estudio/alerta-de-campo write) against the *legitimately* concurrent case — two near-simultaneous writes both trying to `create` a not-yet-existing ficha can race on the `pacienteId` unique constraint (`P2002`); now retried as a plain `update` instead of 500ing.

## Bugfix: Evoluciones largas fallaban con 500 en producción

Causa exacta: `Evolucion.contenido` seguía siendo `String` sin `@db.Text` en `schema.prisma` — Prisma mapea eso a `VARCHAR(191)` en MySQL por default. Una nota clínica de más de 191 caracteres hacía fallar el `INSERT` a nivel base de datos ("Data too long for column 'contenido'"), y el `catch` de `POST /api/evoluciones` (`backend/src/app.ts`) devolvía `{ error: 'failed to create evolucion' }` con status `500` **sin loguear la excepción real** — de ahí que Vercel Logs no mostrara nada útil. El propio código ya documentaba (en el comentario de `contenidoHtml`) que "191 caracteres se queda corto para una nota clínica" — ese fix se había aplicado a `contenidoHtml` cuando se agregó el formato rico, pero nunca se hizo el mismo cambio en `contenido`, el campo original.

**Fix**: `contenido String @db.Text` en el schema; migración `20260817145447_evolucion_contenido_text` (`ALTER TABLE Evolucion MODIFY contenido TEXT NOT NULL`, no destructiva — ensancha el tipo de columna sin tocar filas existentes). Aplicada al dev DB a mano (`prisma db execute` + `migrate resolve --applied`), **no** aplicada a producción (Aiven) — ver el comando exacto que hay que correr, más abajo. `POST`/`PATCH /api/evoluciones` ahora loguean la excepción real con `console.error()` (mismo patrón que ya usaban `PATCH /api/pacientes/:id/ficha-inicial` y antecedentes) y devuelven un mensaje en español ("No se pudo guardar la evolución/los cambios. Volvé a intentar.") en vez del string técnico en inglés — el frontend (`getErrorMessage()`) ya mostraba tal cual cualquier mensaje no vacío del backend, así que alcanzó con corregir el string del lado del servidor, sin tocar frontend.

**Tests**: 6 nuevos en `app.test.ts` (contenido corto, contenido largo ~8400 caracteres sin truncar, `contenidoHtml` largo con formato y sanitización, creación con y sin Diagnóstico junto a contenido largo, edición agregando contenido largo con lectura posterior íntegra). Suite completa: 179 passing (era 173). Nada de frontend se tocó esta ronda — sigue en 81. `tsc`/`npm run build` limpios en backend.

**Comando para aplicar en producción (Aiven)** — no se ejecutó automáticamente, correr manualmente con `DATABASE_URL` apuntando a Aiven:
```bash
npx prisma migrate status
npx prisma migrate deploy
```
Nunca `prisma db push` ni `prisma migrate reset`.
